## 적재 쿼리 4개 — 판단이 갈린 지점

### 1. Paper — 매번 덮어쓴다 (ON CREATE 안 씀)

처음엔 `ON CREATE SET`만 쓰면 될 것 같았다. "적재는 한 번만 도니까 새로 만드는 것만 신경쓰면 되지."
**틀렸다.** 같은 실행 안에서도 인용 때문에 Stub이 먼저 생겨 있다.
페이지 1의 논문이 페이지 300의 논문을 인용하면, 페이지 300이 도착했을 때 그건 CREATE가 아니라 MATCH다.
`ON CREATE`만 쓰면 우리 5만 건 안의 논문이 껍데기로 남는다.

덮어쓰기를 고른 진짜 이유는 "이상한 데이터가 있을 때"가 아니라 **멱등성**이었다.
`restore_abstract` 같은 변환 코드는 한 번에 맞을 리 없고, 고치고 재실행하면 갱신돼야 한다.
ON CREATE만 쓰면 고칠 때마다 DB를 비우고 5만 건을 다시 받아야 한다.

함정 하나: 짧게 쓰겠다고 `SET paper = p` (프로퍼티 통째 치환)를 쓰면
4주차에 넣을 `embedding`이 재실행 때마다 날아간다. 귀찮아도 하나씩 나열.

### 2. Author/Topic — MERGE, Paper — MATCH

여기서 원칙이 하나 나왔다.

> **MERGE는 그 자리에서 완전한 노드를 만들 수 있을 때만 쓴다.**

`authorships` 배열엔 `authorId`와 `name`이 다 있다 → Author는 여기서 완전히 만들 수 있음 → MERGE.
반면 논문은 title도 초록도 없이 `paperId`만 있다 → MERGE하면 ID뿐인 껍데기가 생김 → MATCH.

MATCH는 못 찾으면 그 줄을 조용히 건너뛴다. 관계가 안 생기는 건 아쉽지만
**그래프에 정체불명의 쓰레기가 안 남는다**는 게 더 중요하다.

### 3. 저자를 이름으로 식별하면 안 되는 이유

"저자는 이름만 있으면 되는 거 아냐? 그럼 이름이 곧 저자 아닌가"라고 생각했다.
프로퍼티가 이름뿐인 건 맞는데 **식별자로 쓰는 건 완전히 다른 얘기**였다.

- 동명이인이 뭉친다 — `J. Kim`이 수천 명. 이름으로 MERGE하면 전 세계 J. Kim이 노드 하나
- 같은 사람이 쪼개진다 — `S. Kim` / `Seunghyun Kim` / `Kim, Seung-hyun`

`name`은 정체성이 아니라 **표시용 프로퍼티**고, 정체성은 `openalexId`다.

그리고 이게 0주차에 arXiv를 자른 이유의 진짜 무게였다. 저자 ID가 없으면
저 문제(author disambiguation)를 내가 직접 풀어야 하는데 그건 그 자체로 연구 주제다.
"필드 하나 없어서 탈락"이 아니었다.

### 4. CITES — 원칙을 일부러 어기는 자리

`cited`는 `openalexId`뿐인 껍데기로 만든다. 2번 원칙 위반이다. 그런데 이건 맞는 코드다.

차이는 `ON CREATE SET cited:Stub` 한 줄. **불완전하냐가 아니라 불완전함이 표시되느냐**가 갈랐다.
Author 쿼리에서 MERGE를 썼다면 라벨 없는 껍데기가 생겨서 Full도 Stub도 아닌 정체불명이 된다.
여기 껍데기는 `:Stub`이 붙어서 "일부러 비워둔 노드"임이 그래프에 기록된다.

`ON CREATE`인 것도 이유가 있다. 그냥 `SET`이면 이미 Full인 논문이 인용당했을 때
`:Stub`이 덧붙어서 스키마 v1의 "Full 또는 Stub" 배타성이 깨진다.

(2편 이상이 공통으로 인용한 논문 X를 찾고, 그 X를 공유하는 논문 쌍을 센다)

| 후보 | 건수 | 삼각형/논문 |

NLP가 블록체인의 **8배**. NLP 논문은 전부 같은 고전(Attention, BERT)을 인용하기 때문이다.
`eval.md`에 "벡터 RAG와 그래프 RAG의 차이는 확장 단계 하나뿐"이라고 써놨는데,
데이터에 A→X←B가 없으면 그 확장이 아무것도 못 딸려온다. **5주차 결론이 "차이 없음"으로 끝난다.**

### 내가 틀린 지적을 받았다

"NLP는 LLM이 제일 잘 아는 분야라 도메인 체크리스트 1번이 약하다.
그래서 RAG를 해도 별로 안 나아지는 걸로 보일 위험이 있다"고 정리했는데, **이게 부정확했다.**

`eval.md`에 이미 방어책이 있었다 — **질문 자격 3번: "LLM에 그냥 물었을 때 맞히면 탈락."**
LLM이 아는 걸로 답할 수 있는 질문은 설계상 평가셋에 못 들어온다.

비교가 둘인데 섞어 말한 게 원인이었다.

| | 뭘 재나 | NLP가 유리? |
|---|---|---|
| LLM 단독 vs 벡터 RAG | RAG가 도움이 되나 | 영향 없음 (자격 3번이 거름) |
| 벡터 RAG vs 그래프 RAG | 확장 한 단계가 값을 하나 | **압도적 유리** |

그래서 NLP의 실제 단점은 하나로 줄었다. **평가셋 만들 때 탈락이 많아진다** —
유명한 논문 쌍으로 공통 인용을 물으면 LLM이 그냥 맞혀버린다.
덜 알려진 쌍을 골라야 하고, 5만 건 중 대부분은 안 유명하니 질문 풀 자체는 충분하다. 품이 더 들 뿐.

## 200건 테스트 — 첫 실행

### 실제 데이터에서 바로 터진 것

```python
author_info.get("id", "")   # → None
```

`.get(key, 기본값)`은 **키가 없을 때만** 기본값을 준다. **키가 있는데 값이 `None`이면
`None`이 그대로 나온다.** OpenAlex에 저자 disambiguation이 안 된 논문이 실제로 있어서
`author.id`가 `null`로 온다. `(x.get("id") or "")`로 고쳤다.

오전에 Paper 쿼리를 "매번 덮어쓰기(멱등성)"로 고른 이유가 바로 이런 거였는데,
그날 안에 실제 사례가 나왔다. 변환 코드는 한 번에 안 맞는다.

### 결과

| | 개수 | |
|---|---|---|
| Paper:Full | 200 | 목표대로 |
| Paper:Stub | 17,192 | 인용 대상 |
| Author / Topic | 1,226 / 54 | |
| AUTHORED / HAS_TOPIC | 1,330 / 590 | |
| CITES | 24,373 | 필터 측정 때 센 참고문헌 수와 **정확히 일치** |
| Full+Stub 겹친 노드 | **0** | 배타성 지켜짐 |
| 라벨 없는 Paper | **0** | 껍데기 안 생김 |

`MATCH (p:Full:Stub)`과 `WHERE NOT p:Full AND NOT p:Stub`이 둘 다 0인 게 중요하다.
오전에 정한 두 설계(배타성, MERGE 대신 MATCH)가 실제로 지켜졌다는 증거다.

### Stub → Full 승격 검증

이건 200건만 넣어선 확인이 안 돼서 직접 테스트했다.
Stub 하나를 골라 그 논문의 진짜 데이터를 받아 Paper 쿼리에 넣어봤다.

```
적재 전 → 라벨=[Paper, Stub], title=None
적재 후 → 라벨=[Paper, Full], title="A Dictionary of Hallucinations..."
같은 ID 노드 개수 = 1
```

Stub 떨어지고 Full 붙고 노드는 안 늘었다. 설계대로.

| | 200건 | 1,000건 | 배율 |

| Full | 200 | 1,001 | 5× |
| Stub | 17,192 | 51,860 | **3.0×** |
| CITES | 24,373 | 83,421 | 3.4× |
| Author | 1,226 | 4,343 | 3.5× |
| 소요 시간 | — | 40초 | |
| DB 크기 | — | 4.1MB | |

Stub이 논문보다 **덜** 늘었다. 인용 대상이 겹치기 시작한 것. 5만 건이면 Stub 70~80만, CITES 400만쯤으로 추정.

`Full = 1001`인 건 승격 테스트로 넣은 1건 때문이고, **200건을 다시 넣었는데 중복이 안 생겼다는 증거**다.
오전에 멱등성 때문에 덮어쓰기를 골랐는데 그게 실제로 확인됐다.

### 병목은 Neo4j가 아니라 API 왕복이었다

실행 로그에 `7% cpu`가 찍혔다. **40초 중 37초는 놀고 있었다.**
Neo4j 쓰기가 무거울 거라 걱정했는데(CITES가 페이지당 1.2만 개) 전혀 아니었다.
요청 10번에 40초, 요청당 4초 — 전부 네트워크 대기다.

그래서 `per_page`를 100 → 200(최대값)으로 올려봤다.

```
per_page=100   요청 10회   27.3초  (요청당 2.7초)
per_page=200   요청  5회   15.5초  (요청당 3.1초)   ← 1.8배 빠름
```

데이터가 2배인데 요청당 시간은 2.7 → 3.1초밖에 안 늘었다. **비용은 데이터 양이 아니라 왕복 횟수다.**
5만 건 추정이 23분 → 13분으로 줄었다.

이건 목표 6(토큰을 고려한 설계)이랑 결이 같다. 재보기 전엔 엉뚱한 데를 최적화할 뻔했다.

## 알게 된 것

- **Neo4j 버전은 25.** 벡터 인덱스 요구사항(5.11+)을 훨씬 넘으므로 4주차 임베딩 적재에 문제 없음.
  CLAUDE.md에 "4주차 전까지 확인"으로 미뤄뒀던 항목 해소.
- **`date(null)`은 에러가 아니라 NULL이다.** `publication_date`가 없는 논문이 있어도 안 터진다.
  실제로 cypher-shell에 넣어 확인함.
- **Cypher는 쓰기 절 뒤에 읽기 절이 오면 `WITH`가 필요하다.** `SET ... MATCH ...`는 바로 못 붙임.
- **아무것도 못 찾은 `MATCH`는 행을 통째로 없앤다.** 무결성 검사를 이렇게 이어 붙였더니
  결과가 아예 안 나왔다.
  ```cypher
  MATCH (p:Full:Stub) WITH count(p) AS 겹침
  MATCH (p:Paper) WHERE NOT p:Full AND NOT p:Stub RETURN 겹침, count(p)   -- 출력 없음
  ```
  두 번째 MATCH가 0건이면 앞의 행이 사라져서 집계까지 안 간다.
  **"0이 나와야 정상"인 검사는 따로 돌려야 한다.** 안 그러면 "결과 없음"을 통과로 오해한다.
- **`EXPLAIN`으로 실행 없이 문법 검사가 된다.** DB에 아무것도 안 넣고 쿼리가 말이 되는지만 확인 가능.
- **constraint는 라벨 단위로 걸린다.** `:Paper`에 걸면 `:Paper:Stub`도 똑같이 적용됨.
  Stub이든 Full이든 `openalexId` 하나에 노드 하나가 보장되고,
  나중에 Full 데이터가 들어와도 새 노드가 안 생기고 기존 Stub에 MERGE로 붙는다.
- uniqueness constraint를 걸면 **인덱스가 자동으로 따라온다.** 따로 만들 필요 없음
- 커서 페이징: 첫 요청 `cursor=*` → 응답의 `meta.next_cursor`를 다음 요청에 넣음 → None이면 끝
- `UNWIND`로 100건을 한 번에 보내면 네트워크 왕복이 100번 → 1번. 5만 건에서 차이가 큼

## 백그라운드 실행 — 두 번 틀렸다

5만 건 적재를 백그라운드로 걸고 자려는데, 처음 띄운 방식이 둘 다 잘못돼 있었다.

**1. 진행 상황이 안 보였다.** `python src/ingest.py | tail -30`으로 걸었더니
`tail`이 파이프가 닫힐 때까지 아무것도 안 내보낸다. 로그 파일이 계속 비어 있었다.
파이썬 쪽 버퍼링도 있어서 `-u`가 필요했다.

**2. 세션이 끊기면 같이 죽는다.** `PPID`를 보니 Claude Code 프로세스였다.
터미널 세션이 닫히면 `SIGHUP`을 받고 내려간다. 밤새 돌릴 거면 분리해야 한다.

`setsid`를 쓰려다 **macOS엔 없다**는 걸 알았다(리눅스 전용). `nohup` + `&` + `disown`으로 해결.

```bash
nohup .venv/bin/python -u src/ingest.py > ingest.log 2>&1 < /dev/null &
disown
```

- `nohup` — SIGHUP 무시
- `-u` — 파이썬 출력 버퍼링 해제 (안 하면 로그가 뭉텅이로 늦게 나온다)
- `< /dev/null` — 표준입력 분리
- `disown` — 셸의 작업 목록에서 제거

**여기서 멱등성이 또 값을 했다.** 4분치 진행을 버리고 재시작하는 게 아무 부담이 없었다.
DB를 비울 필요도, 어디까지 했는지 추적할 필요도 없었다.
아침에 죽어 있어도 그냥 다시 돌리면 된다.

## 5만 건 본 적재 완료 — 그리고 표본이 거짓말을 했다

250 페이지, 50,000건. `per_page=200` 덕에 예상보다 빨랐다.

| | 개수 |
|---|---|
| Paper:Full | 50,001 |
| Paper:Stub | 442,054 |
| Author | 94,028 |
| Topic | 701 |
| CITES | 1,144,378 |
| AUTHORED | 133,491 |
| HAS_TOPIC | 138,584 |
| 라벨 겹침 / 정체불명 | **0 / 0** |
| DB 크기 | 214MB |

무결성은 통과. 오전에 정한 설계가 5만 건 규모에서도 깨지지 않았다.

`Full = 50,001`의 +1은 승격 테스트로 넣은 2009년 논문이다. 필터(2020년 이후) 밖인데
Full로 들어가 있으니 나중에 헷갈리지 않게 기억해둘 것. 5만분의 1이라 지우진 않았다.

### 표본 200건이 전체를 대표하지 않았다 ← 오늘 제일 중요한 발견

CITES가 추정치 400만의 1/4인 114만밖에 안 나왔다. 파보니:

| | 논문당 참고문헌 |
|---|---|
| 표본 200건 | **121.9개** |
| 표본 1,000건 | 83.4개 |
| **전체 50,000건** | **22.9개** |

**참고문헌이 0개인 논문이 18,187건(36%)이었다.** OpenAlex가 모든 논문의 인용 목록을
갖고 있진 않다. 그리고 커서 페이징 순서가 무작위가 아니라서 **앞쪽에 기록이 충실한 논문이 몰려 있었다.**
표본을 200 → 1,000으로 늘렸을 때 이미 122 → 83으로 떨어지고 있었는데 그 신호를 못 읽었다.

**이게 왜 심각하냐면**, 오늘 적재 범위를 고른 근거가 그 표본이었다.
"NLP는 삼각형이 논문당 169개"라는 숫자로 후보 6개 중에 NLP를 뽑았는데,
그 169가 과대평가일 가능성이 높다. 후보 간 **상대 비교**는 같은 방식으로 쟀으니 아마 유효하지만,
**절대값은 믿으면 안 된다.**

다음 세션에 전체 그래프에서 실제 삼각형 수를 세봐야 한다. 만약 크게 부족하면
5주차 비교 자체가 위태로우므로 그 전에 알아야 한다.

교훈: **표본으로 재고 끝내지 말 것. 표본 크기를 바꿔가며 값이 수렴하는지 봐야 한다.**
122 → 83은 "아직 안 수렴했다"는 신호였다.

### 초록 없는 논문이 21.5%

`Full` 50,001건 중 초록이 있는 건 39,239건. **10,762건(21.5%)은 초록이 없다.**
4주차에 초록으로 임베딩을 만들 계획인데 이 논문들은 벡터 검색에서 아예 안 잡힌다.
제목으로 대체할지, 그냥 빼고 갈지 4주차에 정해야 한다.

## 블로그로 쓸 만한 것

- **"표본이 거짓말을 했다"** — 논문당 참고문헌이 표본 200건에선 121.9개, 전체 5만 건에선 22.9개.
  표본을 1,000건으로 늘렸을 때 이미 83.4로 떨어지고 있었는데 그 신호를 못 읽었다.
  **수렴을 확인하지 않은 표본은 근거가 아니다.** 그 숫자로 데이터 범위를 결정했다는 점까지 포함해서 글감
- **"병목은 늘 예상 밖에 있다"** — CITES 관계가 페이지당 1.2만 개라 DB 쓰기가 느릴 줄 알았는데
  CPU 7%였다. 전부 API 대기. `per_page` 한 줄로 절반이 줄었다
- **"멱등하게 짜두면 언제든 죽여도 된다"** — 백그라운드 실행이 잘못 걸린 걸 발견하고
  4분치를 버리고 재시작하는 데 아무 고민이 없었다. 설계 하나가 운영 부담을 지운 사례
- **"데이터 범위를 감이 아니라 측정으로 정했다"** — 후보 6개에서 `A→X←B` 삼각형 밀도를 재보니
  8배 차이가 났다. 이론으로 따졌으면 흥미 위주로 골랐을 것
- **`.get(key, 기본값)`은 `None`을 못 막는다** — 키가 있고 값이 `None`인 실제 API 응답
- **0주차에 만진 건 컨테이너와 함께 사라졌다** — 8/10의 "세션 끊기면 날아간다"가
  이번엔 인프라에서 반복됨. 남기는 단위가 문서만이 아니라는 것
