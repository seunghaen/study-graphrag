# 평가 설계와 토큰

4주차부터 쓴다. **평가셋이 잘못되면 5주차 결론 전체가 무너지므로 여기가 프로젝트의 급소다.**

---

## 베이스라인은 셋이다

원래 계획은 4주차 벡터 RAG ↔ 5주차 그래프 RAG 2자 비교였으나, 그것만으로는 결론이 무의미하다.

```
0. LLM 단독 (RAG 없음)   ← 진짜 바닥
1. 벡터 RAG
2. 그래프 RAG
```

**0번이 이미 맞히는 질문은 평가셋에서 제외한다.** 그러지 않으면 4주차에 나오는 높은 정답률이
RAG 성능이 아니라 모델 사전지식이고, 그 위에 그래프를 얹어도 차이가 드러나지 않아
5주차 결론 전체가 무너진다.

### 1번과 2번의 차이는 확장 단계 하나뿐이다

```
벡터 RAG:   초록 top-k          → LLM
그래프 RAG: 초록 top-k → 확장   → LLM
                        ↑ 여기만 다르다
```

벡터 RAG는 그래프 RAG의 부분집합이다. 5주차에 재야 할 것은
**저 확장 한 단계가 정답률을 얼마나 올리고 토큰을 몇 배 쓰는가**다.

---

## 평가 질문의 자격 요건

세 조건을 **모두** 통과해야 한다.

1. 답이 문서 하나에 통째로 적혀 있지 않을 것
2. 그래프 경로를 그릴 수 있을 것 (특히 `A → X ← B` 되돌아오는 패턴)
3. **LLM에 그냥 물었을 때 맞히면 탈락** — 실제로 던져보고 검증한다

통과하는 질문은 보통 **전부 / 몇 개 / 합계 / 평균 / 교차**가 들어간다.
검색은 적힌 것을 찾아오고, 그래프는 적히지 않은 것을 계산한다. 후자만 평가 대상이다.
**완전성 보장**(웹 검색은 "찾은 것"을 주지 "전부"를 보장하지 않음)도 그래프의 고유 강점이다.

---

## 토큰은 측정 항목이 아니라 설계 제약이다

학습 목표 6번. 원래 5주차에만 있었으나 **4주차 벡터 RAG 베이스라인부터 제약으로 적용**한다.
5주차에 재보기만 하면 "비교해봤다"로 끝나고 "고려한 설계"는 남지 않는다.

### 왜 4주차부터인가

베이스라인에 계측이 없으면 5주차 비교는 숫자 없는 인상평이 된다.
벡터 RAG를 만들 때부터 질문당 입력 토큰이 찍혀야 그래프 검색이 그걸 이겼는지 졌는지 말할 수 있다.

### 토큰을 결정하는 설계 지점

- **청킹 전략** — 청크 크기와 top-k가 곧 입력 토큰이다. 512토큰 × 5개와 2048토큰 × 3개는 성격이 다르다
- **서브그래프 직렬화 방식** — 그래프 검색 결과를 LLM에 어떻게 넣느냐에 따라 토큰이 배 단위로 갈린다.
  트리플 나열, 자연어 문장화, 압축 스키마 표현이 각각 다르다. **여기가 GraphRAG의 핵심 설계 지점이다**
- **홉 수** — 홉을 늘리면 노드가 지수적으로 늘어난다. 2홉과 3홉은 토큰 규모가 다른 문제다.
  가지치기(엣지 타입 제한, 스코어 컷) 없이 홉만 늘리면 컨텍스트가 터진다
- **프롬프트 고정 비용** — 시스템 프롬프트, 스키마 설명, few-shot 예시. 질문마다 반복해서 붙는다
- **에이전트 간 메시지 전달** (7주차) — 멀티에이전트는 같은 컨텍스트가 에이전트 수만큼 복제된다
- **임베딩 API 호출** — 적재할 때(논문 전체)와 검색할 때(질문마다). 적재 쪽이 일회성이지만 규모가 크다

### 측정 지표

질문당 입력/출력 토큰, 정답률, 그리고 **토큰당 정답률**.
마지막 것이 없으면 "그래프가 더 정확한데 토큰을 3배 쓴다"는 상황을 평가할 수 없다.

### 결론으로 끌고 갈 질문

"그래프가 더 낫다"가 아니라 **"어떤 질문 유형에서, 토큰 몇 배를 쓰고, 정확도가 얼마나 올랐나"**.
이게 목표 5번의 실질적 산출물이다.
