같은 논쟁을 반복하거나 이미 폐기한 선택지로 되돌아가려 할 때 이 문서로 먼저 검증한다.

## 1. 멀티에이전트는 목표가 아니라 비교 대상이다 (2026-08-02)

사용자가 멀티에이전트를 만들고 싶어 한다. 받되, **단일 에이전트를 먼저 만들고 멀티가 이기는지 비교**한다.

```
6주차: 단일 에이전트 + 도구들       ← 베이스라인
7주차: 라우터가 전문 에이전트에 분배  ← 비교 대상
```

베이스라인 3개를 만든 것과 같은 논리다. 답해야 할 질문은 "멀티에이전트를 만들었다"가 아니라
**"어떤 질문 유형에서 멀티가 단일보다 낫고, 토큰을 몇 배 쓰나"**다.
실제로 대부분의 문제는 단일 에이전트 + 잘 만든 도구로 풀린다. 그걸 직접 확인하는 것이 학습이다.

이 순서면 7주차가 안 끝나도 6주차 결과물이 남는다.

멀티에이전트는 토큰이 폭발한다. 목표 6번의 좋은 재료다.

## 2. 라우터가 고르는 것은 DB가 아니라 검색 전략이다 (2026-08-04 수정)

```
              [라우터 에이전트]
             "이 질문 어떻게 풀지?"
          ↙          ↓          ↘
   [벡터만]   [벡터 → 그래프 확장]   [그래프만]
 "비슷한 논문"   "그 논문들의 저자 전부"  "Kaiming He의 공저자"
```

**원래 그림은 `[벡터 검색] ↔ [그래프 검색]` 2지선다였으나 틀렸다.**
둘은 경쟁 관계가 아니라 역할이 다르다. 벡터가 **어디서 시작할지**를 찾고,
그래프가 **거기서 뭘 끌어올지**를 한다. 그리고 재밌는 질문은 대부분 가운데 갈래다.

목표 5번은 "벡터DB와 그래프DB 차이를 알고 **선택**할 수 있기"다.
이 구조는 그 선택을 시스템이 수행하게 만든다 — 아는 것을 코드로 표현하는 단계.
그래프가 멀티에이전트 확장에 밀려 빠지는 것도 이 구조가 막는다.

## 3. 벡터는 Neo4j 안에 넣는다 — 별도 벡터DB 없음 (2026-08-04)

Neo4j 5.11+는 벡터 인덱스를 내장한다. 임베딩은 별도 저장소가 아니라 **노드 프로퍼티 하나**다.

```
(:Paper {
    openalexId: "W2194775991"
    title:      "Deep Residual Learning for Image Recognition"
    abstract:   "Deeper neural networks are more difficult..."
    embedding:  [0.021, -0.13, 0.44, ...]      ← 벡터 인덱스가 걸리는 프로퍼티
 })
    ├─[:AUTHORED_BY]→ (:Author {id: "A5100700361", ...})
    └─[:CITES]→       (:Paper {...})
```

같은 노드가 벡터도 갖고 관계도 갖는다. 그래서 벡터로 찾은 논문에서 **한 쿼리 안에서** 바로 관계를 탄다.

```cypher
CALL db.index.vector.queryNodes('paper_abstract', 20, $questionVector)
YIELD node AS p
MATCH (p)-[:AUTHORED_BY]->(a:Author)
RETURN DISTINCT a.name
```

### Pinecone/Qdrant를 따로 두지 않는 이유

- 목표 5번의 알맹이는 제품 API 차이가 아니라 **검색 방식 차이**다. Neo4j 하나 안에서도 그대로 비교된다
- DB가 하나면 인프라 변수가 제거돼 5주차 비교가 깨끗해진다
  (그래프가 느린 건지 네트워크 왕복이 느린 건지 구분 가능)
- 분리하면 2주차 적재가 두 번, 3주차 AWS 인프라가 하나 더, 동기화 깨짐 디버깅이 추가된다.
  **버퍼가 없는 계획에서 그 며칠은 7주차 멀티에이전트에서 빠진다**
- 데이터가 논문 수만 건 규모다. 전용 벡터DB가 이기는 구간(수천만~억 건)이 아니다

분리가 맞는 경우는 벡터가 수천만 건 이상이거나 이미 사내에 벡터 스택이 있는 상황이다. 이 프로젝트는 아니다.

### 임베딩은 Neo4j가 만들어주지 않는다

초록을 임베딩 모델(Bedrock 등)에 보내 배열을 받아 넣는 것은 파이프라인의 일이다.
**적재할 때와 검색할 때 같은 모델을 써야 한다.** 다르면 좌표계가 달라 유사도가 무의미해진다.
이 임베딩 API 호출도 4주차 토큰 계측 대상이다.

### 검증 필요

도커로 띄운 Neo4j 버전 확인 (벡터 인덱스는 5.11+). 4주차 임베딩 적재 전까지.

## 4. 데이터 소스는 OpenAlex 단독 (2026-08-04)

판정 근거 전체는 [week0-data.md](week0-data.md) 참고. 요약만 남긴다.

- **arXiv 탈락** — 인용 관계 없음, 저자가 이름 문자열뿐(동명이인 구분 불가)
- **Semantic Scholar 보류** — 익명 호출이 429(전 세계 공용 한도). API 키 신청 시 며칠 소요
- **OpenAlex 채택** — 인용·저자ID·집계 전부 있고, 무료 한도 안에서 적재 가능

arXiv를 병행해 붙이는 안은 폐기했다. 얻는 건 원문 초록 하나인데(OpenAlex는 뒤집힌 형태로 주고
복원에 20줄이면 된다) DOI/arXiv ID 매칭 작업이 2주차에 통째로 추가된다. 값이 안 맞는다.

## 5. 3주차에 풀어야 할 것 — Neo4j를 어디에 두나 (미결)

로컬 도커 Neo4j는 **Bedrock 에이전트가 접근할 수 없다.** Lambda는 사용자 노트북의
`localhost:7687`을 보지 못한다. 6주차에 이걸 발견하면 그 주가 통째로 인프라 삽질이 된다.

4주차까지는 로컬로 개발하되, **로컬은 영구 집이 아니다.**
EC2에 올릴지, 관리형을 쓸지는 3주차에 결정한다. Neptune은 비용 때문에 배제했다.

## 6. 도메인 선정이 세 번 실패한 이유 (2026-08-02)

**사용자의 흥미는 데이터가 아니라 시스템에 있다.**
무언가를 **만드는** 데 흥미가 있지 **수집하고 정리하는** 데 흥미가 없다.
"어떤 데이터가 재밌냐"고 물으면 답이 안 나온다.

그래서 순서를 뒤집었다. **시스템(멀티에이전트)을 먼저 정하고 데이터는 조연으로 깐다.**
논문 도메인은 흥미 때문이 아니라 데이터 가용성 때문에 골랐고, 그래도 된다.

**운영 지침:** 도메인 흥미가 낮다는 것은 동기가 시스템 쪽에 걸려 있다는 뜻이므로,
막힐 때는 데이터 작업보다 시스템 작업 쪽으로 진도를 빼는 게 회복이 빠르다.
